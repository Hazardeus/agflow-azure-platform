# Development Workflow

This document defines how changes are developed, validated, documented, and promoted in the `agflow-azure-platform` repository.

## 1. Development principles

Development must be incremental.

Do not implement the complete Azure platform in a single change.

Each milestone must introduce one coherent infrastructure capability, be reviewed, validated, and documented before moving to the next milestone.

The current project status and next milestone are defined in `STATUS.md`.

Before starting work, agents and contributors must read:

1. `../AGENTS.md`
2. `ARCHITECTURE.md`
3. `STATUS.md`
4. relevant ADRs under `adr/`
5. any scoped instructions applicable to the files being modified

## 2. Infrastructure ownership

Infrastructure ownership is defined in `ARCHITECTURE.md` and formally recorded in ADR-0001.

The primary rule is:

> A resource must never be managed by both Bicep and OpenTofu.

Current ownership boundaries are:

* Bicep: long-lived Azure platform infrastructure.
* devpod-ui / OpenTofu: ephemeral workspace infrastructure.
* Docker Compose: applications running on the control-plane VM.

Changes must preserve these boundaries unless a new ADR explicitly supersedes the existing decision.

## 3. Change workflow

For every meaningful change:

1. Read the current project documentation.
2. Confirm the current milestone in `STATUS.md`.
3. Propose the intended change.
4. Identify whether the change introduces an architectural decision.
5. Implement only the requested milestone.
6. Run local validation.
7. Review the resulting diff.
8. Run Azure `what-if` before any deployment.
9. Update documentation when required.
10. Commit the completed, validated change.

Do not deploy Azure resources unless deployment has been explicitly requested.

## 4. Bicep validation

For Bicep changes, run at minimum:

```powershell
az bicep lint --file infra/main.bicep
az bicep build --file infra/main.bicep
az bicep build-params --file infra/environments/lab/main.bicepparam
```

Before deployment, run a subscription-level `what-if`:

```powershell
az deployment sub what-if `
  --location swedencentral `
  --template-file infra/main.bicep `
  --parameters infra/environments/lab/main.bicepparam
```

A real deployment must not be executed until the `what-if` output has been reviewed.

## 5. Documentation responsibilities

Documentation is part of the implementation.

### Update `STATUS.md` when

* a milestone starts or completes;
* a major capability becomes available;
* the next planned milestone changes;
* an important blocker appears or is resolved.

### Update `ARCHITECTURE.md` when

* the current system structure changes;
* component responsibilities change;
* ownership boundaries change;
* networking or security architecture changes;
* a new major platform component is introduced.

`ARCHITECTURE.md` describes the resulting architecture, not the chronological history of changes.

### Create an ADR when

A decision:

* affects infrastructure ownership;
* introduces or replaces a major Azure service;
* changes networking or security posture;
* changes identity or RBAC strategy;
* affects the control-plane architecture;
* changes the Bicep / OpenTofu / Docker Compose boundary;
* introduces a significant dependency;
* is difficult or costly to reverse.

Do not create ADRs for trivial implementation details.

Accepted ADRs must not be silently rewritten when a decision changes. Create a new ADR that supersedes the previous one.

## 6. Git history versus ADRs

Git history records what changed.

ADRs record why an important architectural decision was made.

Project documentation records the current resulting state.

Do not create verbose AI activity logs or work journals duplicating Git history.

## 7. Secrets and sensitive data

Never commit secrets.

Secrets must not appear in:

* `.bicep` files;
* `.bicepparam` files;
* documentation;
* Git history;
* outputs;
* cloud-init;
* example commands with real credentials.

Environment parameter files committed to Git must contain only non-sensitive configuration.

## 8. Generated artifacts

Compiled ARM JSON generated by Bicep is considered build output and should not be committed unless an explicit future requirement changes this policy.

Bicep source files remain the source of truth.
